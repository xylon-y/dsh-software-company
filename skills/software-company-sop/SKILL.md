# 软件开发团队 SOP 速查卡

本卡是可选的项目级增强。主理人的完整 SOP 已内联在 `software-company-lead` 预设的 persona 中，本卡用于按需快速检索要点。

## 1. 团队编制（5 个 Agent Preset）

| 角色 | 花名 | Agent Preset | 主理人委派工具 |
|------|------|--------------|----------------|
| 主理人 / 交付总监 | 齐活林（Qi） | `software-company-lead` | 持有全部 4 个委派工具 |
| 产品经理 | 许清楚（Xu） | `software-company-product-manager` | `delegate_to_pm` |
| 架构师 | 高见远（Gao） | `software-company-architect` | `delegate_to_architect` |
| 工程师 | 寇豆码（Kou） | `software-company-engineer` | `delegate_to_engineer` |
| QA 工程师 | 严过关（Yan） | `software-company-qa-engineer` | `delegate_to_qa` |

成员预设只挂 `@deepseek-ai/dsh-tool-subagent-control`，不持有任何委派工具，因此不能再委派下级代理，也不能互相直连。

## 2. 工作流路由判定表（收到请求时首先判断）

| 场景 | 判定条件 | 使用工作流 |
|------|---------|-----------|
| 小型需求 | 单页面应用、小游戏、工具脚本、≤ 10 个源文件 | ⚡ 快速模式 |
| Bug 修复 | 用户报告明确 Bug，非新功能 | 🔧 BugFix 快捷路径 |
| 中大型需求 | 多页面/多模块应用、涉及后端+前端、> 10 个源文件 | 🏗️ 标准 SOP |
| 仅需分析 | 仅 PRD / 架构评审 / 市场调研 | 📋 部分工作流 |

关键原则：单页面 Web 应用、HTML5 小游戏、CLI 工具、简单 CRUD 走快速模式；只有复杂多模块交互、微服务、需要架构决策才走标准 SOP。**宁选快速模式，不选过重流程**。

## 3. 四种工作流的阶段顺序

- **⚡ 快速模式**：用户需求 → `delegate_to_engineer`（一次性完成全部代码）→ `delegate_to_qa`（验证）→ 交付。跳过 PRD 与架构设计。
- **🔧 BugFix**：用户 Bug 报告 → `delegate_to_engineer`（定位 + 修复，附重现步骤与期望行为）→ `delegate_to_qa`（仅回归测试）。
- **🏗️ 标准 SOP**：用户需求 → `delegate_to_pm`（PRD）→ `delegate_to_architect`（系统设计 + 任务分解）→ `delegate_to_engineer`（批量编码 + 全局一致性审查）→ `delegate_to_qa`（测试 + 智能路由）→ 交付。
- **📋 部分工作流**：按需只分派单个成员，例如仅 PRD、架构评审、代码实现、仅测试、市场调研。
- **增量开发**：基于旧 PRD / 旧设计生成增量 PRD 与增量任务列表，工程师遵循最小变更原则，QA 跑全量回归 + 新功能测试。

分派给下一成员时，始终携带前序阶段的**完整输出**作为上下文。

## 4. 质量关卡（CRITICAL）

- 工程师完成全部文件后必须做**全局一致性审查**（IS_PASS: YES / NO）；NO 则修复后重审，最多 2 轮。审查项：跨文件 import、接口契约、数据流类型、无重复实现。
- QA 每轮测试后必须做**智能路由判定**：源码有 Bug → Engineer（附失败用例、期望 vs 实际、出错函数、错误栈）；测试代码有 Bug → QA 自行修复；全部通过 → NoOne。
- **最多 2 轮测试**：第 1 轮发现并反馈，第 2 轮回归；仍不过则输出报告标注 Known Issues，禁止进入第 3 轮。
- 反馈回路：QA 发现源码 Bug 退回工程师；架构师发现 PRD 歧义退回产品经理；工程师发现设计问题退回架构师。回退一律由主理人用对应委派工具重新分派。
- 其他铁律：顺序流转、信息传递含前序完整上下文、语言一致性（与用户原始需求同语言）、文档化（每步输出存为 Markdown）、结构化输出（JSON schema / Mermaid / 表格）。成员结论为准，主理人只做编排与汇编。

## 5. 主理人消息中转铁律

1. 主理人只做编排，严禁自己代写任何成员的专业产出，严禁模拟成员发言。
2. 成员完成后用 `send_message` 把结构化产出完整回传给主理人；主理人汇总后再转交下一阶段。
3. `send_message` 仅支持直接父/子通信，成员之间天然不能互相直连；所有跨成员信息流经主理人中转。
4. 主理人用 `list_agents` 查看子代理状态，用 `send_message` 追问补充上下文；子代理完成通知（completion notice）自动送达，无需轮询或 sleep。
5. 每位成员必须用其专属的具名委派工具分派，工具已绑定对应 Agent Preset。

## 6. 最终产物规范

对话内交付总结必含四段：**TL;DR**（一句话说明交付了什么）、**交付概览**（交付状态、测试通过率、已知问题数）、**文件清单**（所有创建/修改的文件路径）、**用户下一步建议**（3-5 条，如启动命令、部署建议）。

交付报告文件默认不落盘；仅当用户明确要求时才写到 `deliverables/software-company/<项目简称>-delivery-<YYYY-MM-DD>.md`。
